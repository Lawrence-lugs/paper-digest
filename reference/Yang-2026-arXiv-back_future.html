Back to the Future: Rethinking EDA Infrastructure for Agentic Systems in Chip Design Verification

Je Yang (Columbia University; work done while interning at Google), Ivan Lobov (Google DeepMind), Thomas Karpati (Google)

Verdict. A sensible, cheap pattern: load the VCD into a two-table SQLite store, prune clocks and silent nets, and let tool-calling agents query it. The evidence is thin: a self-built 150-query benchmark scored 143/150 with no external baseline, no accuracy-under-pruning run, and a thesis (infrastructure, not model capability, is the bottleneck) that is never tested without the database. Reuse the idea and treat the numbers as illustrative; the weakest points are the undefined "coverage" metric and root-cause analysis that is advertised but never evaluated. overall confidence 70%

Motivation86%

The authors argue that LLM-for-EDA work is lopsided: approximately 74.6% of studies target static RTL generation, so post-simulation waveform debugging is neglected, even though verification is said to take over 70% of the design cycle. Engineers debug by scrubbing waveform viewers, while agents are locked out because raw ASCII dumps exceed context windows by orders of magnitude, carry no semantic index and expose no query interface. The paper names this gap "Infrastructural Impedance".

Convincing? The pain point is real and the diagnosis (agents see logs, humans see waveforms) is persuasive. The two supporting statistics are weaker than they look: 74.6% comes from a 2024 scoping review that cannot reflect the 2025-26 agentic wave, and the 70% figure is cited to a Cadence web page.

Core idea88%

Two coupled parts. Offline, a VCD dump is loaded into SQLite as signal_metadata (id, RTL signal name, variable type) and signal_changes (timestamp, value, foreign key to metadata), with rows pruned at insertion. Online, an orchestrator and three agents turn natural-language questions into tool or SQL calls over that database.

The pruning policies, as I formalize the paper's prose (it gives no equation): let \(n_s\) be the transition count of signal \(s\), \(S\) the set of signals and \(\mathcal{C}\subseteq S\) the clocks.

\[ \mathrm{keep}(s)\iff s\notin\mathcal{C}\ \wedge\ n_s\ge\tau,\qquad \tau_{\text{zero}}=1,\quad \tau_{\text{avg}}=\bar n=\frac{1}{|S|}\sum_{s\in S}n_s \]

Table 1 appears to apply the policies cumulatively. Splitting its reductions into marginal contributions shows that clock removal does nearly all the work (percentage points of the unpruned 1,420 MB):

\[ 86.97\%\;\approx\;\underbrace{66.2}_{\text{clocks}}+\underbrace{6.0}_{\text{zero-toggle}}+\underbrace{14.8}_{\text{below-average}}\ \text{pp} \]
  • Orchestration Agent: decomposes the query into sub-goals, routes them and audits the merged answer.
  • Analysis Agent: composes queries for scope discovery, event inspection and toggle counting, with an iterative function-calling loop for hotspots.
  • Verification Agent: ties waveform anomalies to versioned source by matching five SVA macro names (ASSERT, ASSERT_STATIC, ASSERT_NEVER, ASSERT_KNOWN, COVER) with regular expressions.
  • Evaluation Agent: audits candidate queries on correctness, completeness, efficiency, schema adherence and context understanding.

Agents communicate only through a shared session context, with a self-correction loop on failed queries. My read: the pruning pipeline is the only part with a measured trade-off. The agent layer gets equal billing in the paper, so I treat it as a second core idea even though its evidence is thin.

Distinguishing factor62%

  • LLM RTL-generation and verification agents (VeriMoA, MAGE, UVLLM, FVEval). The paper says these work on static source, assertion lists or small simulation logs, and BTTF differs by consuming simulation waveforms. I did not open these papers to check that characterization.
  • Waveform-aware coding agents (VerilogCoder, AST-based waveform tracing). The closest prior work, dismissed as tied to small code-centric examples. There is no head-to-head run, so the difference in scale is asserted, not shown.
  • Text-to-SQL (Gao et al. 2023). Used as an enabling capability, not extended. With two tables the SQL itself is easy; the hard parts are scope-name resolution and timescales, which the paper handles with helper tools.
  • Not discussed: conventional waveform tooling such as viewer scripting, vendor waveform-database APIs and Python VCD parsers (from my background knowledge, unverified). A VCD already consists of declarations plus timestamped changes, which is exactly the two tables, so the schema is a transcription. The contribution is the pruning policies and the agent tool layer.

No earlier version by the same authors is cited, so there is no comparison to a prior BTTF.

In case you missed it70%

−Root-cause analysis is advertised, not evaluated. Table 2 has no root-cause category, and the "backward causal tracing" of Appendix A.1 looks up the prior values of the assertion's own operands, which names the violating symptom rather than a cause upstream in the design. The intro's "formal verification" is dynamic assertion checking on a single trace.
−Less open-ended than "text-to-SQL" suggests. The Verification Agent is five hard-coded macro names matched by regex plus per-rule checkers such as verify_known_rule, and most Analysis Agent actions in Table 3 are named helper functions. This is closer to natural-language tool selection.
−Pruning blind spots. Zero-toggle pruning drops constant values, yet a signal that never moves is a common bug symptom. Clock pruning is justified by timestamps preserving temporal anchoring, but the paper never says the clock period is stored, while the ASSERT_KNOWN example samples at clock edges and the A.1 example reports a net going unknown "while clk was high".
−Scale gap. The motivation talks about terabytes and dumps above 10 GB; the benchmark is 4.2 GB, 18,450 nets and 50 to 800 ns windows, and the unpruned database (1,420 MB) is already smaller than the VCD. No code or benchmark release is mentioned.
·"On-the-fly" is doing a lot of work. Pruning by the design-wide average toggle rate needs global statistics, so it cannot be single pass, the ingestion cost of that policy is not reported, and streaming ingestion is listed as future work.
·Loose citations. A prefix-caching systems paper (KVflow) and a Copilot robustness study are cited as EDA-verification evidence, in a reference list of only 12 entries.
+Right kind of boring. Windowed and aggregate questions (toggle counts, first time a value occurs) are exactly what a context window cannot hold and a database answers trivially, and Table 3 gives concrete calls that make the design easy to reimplement.
+An explicit lossy boundary. The pruning ladder with a stated 35.77% coverage loss is the most reusable contribution, once the fidelity metric is defined.
